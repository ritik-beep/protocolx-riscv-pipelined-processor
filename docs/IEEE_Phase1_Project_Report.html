Abstract—
In digital computer systems, pipelining is the fundamental technique used to boost instruction throughput and keep hardware blocks busy. Instead of completing an entire instruction within one long clock cycle before starting the next, a pipelined processor overlaps the execution of multiple instructions like an assembly line. In this Phase I project, our team (ProtocolX) designed, implemented, and verified a 32-bit 5-stage pipelined processor in synthesizable Verilog HDL based on the open RISC-V (RV32I) instruction set architecture. The processor datapath is split into five balanced stages: Instruction Fetch (IF), Instruction Decode (ID), Execute (EX), Memory Access (MEM), and Write-Back (WB), separated by four pipeline registers. To prevent incorrect execution from data dependencies and branches, we developed a centralized Hazard Detection and Forwarding Unit. This unit resolves Read-After-Write (RAW) data hazards through operand forwarding, stalls load-use dependencies for one cycle, and flushes instructions fetched during taken branches. We thoroughly simulated the design using Icarus Verilog across arithmetic programs, hazard forwarding tests, memory operations, and branch flushes. All 42 automated verification assertions passed with zero errors, confirming a working, verifiable Phase I prototype.

I. Introduction

When students first study processor design in computer organization courses, central processing units are usually explained as single-cycle machines. In a single-cycle CPU, every instruction must be fetched from memory, decoded, executed in the ALU, read from or written to data memory, and finally written back into the register file—all within one clock cycle. Because the clock period must be set long enough to accommodate the slowest possible instruction (usually Load Word, LW), the processor is forced to run at a low clock frequency, and most hardware modules sit idle during any given slice of time.

Pipelining addresses this fundamental performance problem by breaking instruction execution into sequential, independent stages. In our project, we chose the classic 5-stage RISC microarchitecture. We chose the open-source RISC-V instruction set (specifically the base integer subset, RV32I) because of its clean, modular instruction encoding, fixed 32-bit length, and lack of historical microarchitectural baggage like condition-code registers or delay slots.

The primary objective of Phase I was to build a clean, working, and verifiable 5-stage pipelined processor in Verilog HDL. Our design prioritizes functional correctness, real test evidence, and proper hazard mitigation over theoretical claims.

II. Literature Review

Before starting RTL coding, our team conducted a literature survey of processor architectures, the RISC-V instruction set manual, and established pipeline hazard resolution strategies.

1) RISC-V Base Integer Specification: Waterman and Asanović [1] defined the unprivileged RV32I specification. RV32I uses four core instruction formats: R-type (register-register), I-type (immediate/load), S-type (stores), and U-type (upper immediate), along with two variations (B-type for conditional branches and J-type for unconditional jumps). The destination register (rd) and source registers (rs1, rs2) always appear at the exact same bit positions across all formats, which dramatically simplifies instruction decode logic in hardware.

2) Classical 5-Stage Pipelining: Patterson and Hennessy [2] formulated the standard 5-stage RISC pipeline consisting of Instruction Fetch (IF), Instruction Decode (ID), Execution (EX), Memory Access (MEM), and Write-Back (WB). They showed that pipeline registers between stages are required to latch intermediate state on the rising clock edge, allowing up to five instructions to be in flight simultaneously.

3) Pipeline Hazards and Mitigations: Hennessy and Patterson [3] classified pipeline hazards into three distinct categories:

a) Structural Hazards: Resource conflicts where two stages attempt to access the same hardware unit simultaneously. In our design, we eliminate structural memory hazards by adopting a Harvard-style split memory architecture (separate instruction memory and data memory).

b) Data Hazards: Occur when an instruction depends on the result of an earlier instruction that has not yet reached the write-back stage (Read-After-Write, or RAW). Rather than wasting multiple clock cycles with stall bubbles, data forwarding (or bypassing) routes the newly computed value directly from the EX/MEM or MEM/WB pipeline registers into the ALU inputs.

c) Control Hazards: Occur when branch or jump instructions change the program flow. Because branch conditions are typically evaluated in the EX stage, subsequent instructions have already entered the IF and ID stages. If the branch is taken, those instructions must be safely flushed.

4) Open-Source Academic Implementations: We also examined simple open-source RISC-V implementations such as Claire Wolf's PicoRV32 [4] and Olof Kindgren's SERV [5]. While PicoRV32 uses a state-machine multi-cycle approach to minimize area, and SERV uses a bit-serial datapath, our goal for ProtocolX was to build a parallel 5-stage pipeline with real-time forwarding to maximize instruction throughput.

III. Proposed Solution

Our processor microarchitecture is built around five distinct pipeline stages, four pipeline barrier registers, and a centralized Hazard Detection and Forwarding Unit.

A. Overall Architecture

Fig. 1. ProtocolX 5-Stage Pipelined RISC-V Processor Block Diagram

B. The Five Pipeline Stages

1) Instruction Fetch (IF): The Program Counter (PC) register stores the 32-bit byte address of the instruction to be fetched. At every positive clock edge, if the PC write enable signal (pc_write) is asserted, the PC increments by 4 (PC + 4) to fetch the next sequential word. When a branch or jump occurs, a 2-to-1 multiplexer selects the target address computed in the EX stage instead. Instructions are read from a 4KB instruction memory model.

2) Instruction Decode (ID): The 32-bit instruction is unpacked into its bitfields: opcode (bits [6:0]), destination register rd (bits [11:7]), function codes funct3 (bits [14:12]) and funct7 (bits [31:25]), and source registers rs1 (bits [19:15]) and rs2 (bits [24:20]). The Register File contains 32 general-purpose 32-bit registers. Register x0 is hardwired to zero (reads always return 0, writes to x0 are ignored). To avoid a structural race condition when an instruction reads a register in the same clock cycle it is being written by the write-back stage, we built internal write-through bypass logic into the register file. The Immediate Generator extracts and sign-extends constants for I, S, B, U, and J instructions. The Control Unit generates all downstream control signals.

3) Execute (EX): The 32-bit ALU performs arithmetic, bitwise, shift, and comparison operations. Forwarding multiplexers select whether ALU operand A and operand B come from the decoded register values or are forwarded from the EX/MEM or MEM/WB pipeline registers. A dedicated branch adder computes the jump target address:

$$\text{Target PC} = \text{Base Address} + \text{Immediate}$$

For conditional branches and JAL, the base address is the instruction's own PC. For JALR, the base address is the forwarded value of register rs1. The EX stage evaluates the branch condition (BEQ, BNE, BLT, BGE, BLTU, BGEU) and asserts branch_taken when true.

4) Memory Access (MEM): Connects to the 4KB synchronous Data Memory. On store instructions (SW), the forwarded rs2 data is written into memory on the positive clock edge at the effective byte address computed by the ALU. On load instructions (LW), 32-bit data is read asynchronously from memory. Non-memory instructions simply propagate their ALU result through to the next stage.

5) Write-Back (WB): A 3-to-1 multiplexer chooses whether the destination register receives: (a) the ALU computation result (mem_to_reg = 2'b00), (b) data read from memory (mem_to_reg = 2'b01), or (c) PC + 4 (mem_to_reg = 2'b10, used to store return addresses for JAL and JALR).

C. Pipeline Registers

Four edge-triggered registers synchronize data between stages:

• pipe_if_id: Latches PC, PC + 4, and instruction word. Features an active-high enable line (to freeze during load-use stalls) and a synchronous flush line (to inject NOP on taken branches).

• pipe_id_ex: Latches register operands, immediate value, register indices (rs1, rs2, rd), PC, function fields, and control signals. Includes a synchronous flush line.

• pipe_ex_mem: Latches ALU result, forwarded store data, destination register index, and memory read/write control signals.

• pipe_mem_wb: Latches loaded memory data, ALU result, destination register index, and register write enable signal.

E. Implementation Approach & Verilog Structure

The design was implemented strictly following clean, modular RTL coding principles in Verilog HDL. Each hardware entity was built as an independent module with cleanly defined inputs and outputs.

The top-level module (riscv_core.v) instantiates the stage modules, registers, and memories. A centralized header file (riscv_defines.vh) ensures parameters such as word width (XLEN = 32), register address width (5 bits), and ALU operation encodings remain uniform across the entire codebase.

F. Hazard Detection and Forwarding Unit

The hazard management unit operates continuously in parallel with the datapath:

1) RAW Data Forwarding: When an instruction currently in the EX stage reads register rs1 or rs2, the hazard unit checks if an earlier instruction in the EX/MEM stage is writing to that register: 

if (reg_write_mem && (rd_mem != 0) && (rd_mem == rs1_ex))
    forward_a = 2'b10; // Forward from EX/MEM
else if (reg_write_wb && (rd_wb != 0) && (rd_wb == rs1_ex))
    forward_a = 2'b01; // Forward from MEM/WB

Identical logic applies to operand B (forward_b). This allows dependent instructions to run without any pipeline bubbles.

2) Load-Use Data Hazard: When an instruction immediately follows a load instruction and requires the loaded value, forwarding from the EX stage is physically impossible because memory read data is not ready until the end of the MEM stage. The hazard unit detects this exact condition: 

if (mem_read_ex && (rd_ex != 0) && 
   ((rd_ex == rs1_id) || (rd_ex == rs2_id))) begin
    pc_write    = 1'b0; // Freeze PC
    if_id_write = 1'b0; // Freeze IF/ID register
    id_ex_flush = 1'b1; // Inject NOP into ID/EX
end

This creates exactly one bubble cycle, after which data forwarding from MEM/WB delivers the loaded data to the ALU.

3) Control Hazard Handling: When a conditional branch or jump evaluates to taken in the EX stage, the two instructions fetched along the fall-through path are flushed by asserting if_id_flush = 1 and id_ex_flush = 1, while redirecting the PC to the branch target.

B. Verification of Load-Use Stall

In test tb_riscv_mem.v, instruction LW x2, 0(x0) was immediately followed by ADDI x3, x2, 50. As shown in Figure 2, at Cycle 4 the hazard unit detected that x2 was still being loaded from memory. It lowered pc_write and if_id_write to 0, holding the PC at address 0x10, and injected a NOP bubble into the ID/EX register. In Cycle 5, execution resumed cleanly, and register x3 received the correct value (150) without data corruption.

C. Verification of Branch Flushing

In test tb_riscv_branch.v, a BEQ x1, x2, 12 instruction evaluated to taken at Cycle 4. The hazard unit immediately asserted if_id_flush = 1 and id_ex_flush = 1. The two instructions fetched along the fall-through path (which attempted to write 99 into registers x3 and x4) were converted to NOPs. Our post-simulation register audit confirmed that registers x3 and x4 remained strictly 0, and the target instruction executed correctly, writing 42 into register x5.
